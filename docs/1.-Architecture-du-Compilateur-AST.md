# 1. Architecture du Compilateur AST

Le compilateur de GPUsync est un compilateur Juste-à-Temps (JIT) qui convertit le code Python en kernels natifs CUDA C++, OpenCL C99, LLVM JIT CPU, et assembleur GPU NVIDIA PTX à la volée. Cette approche permet au développeur de coder dans une syntaxe Python épurée tout en profitant des performances brutes des GPUs et des processeurs.

---

## Structure du sous-package `gpusync/compiler/`

Le compilateur est structuré en plusieurs modules sous [gpusync/compiler/](https://github.com/GalTechDev/GPUsync/tree/main/gpusync/compiler) :

### A. [compiler/base.py](https://github.com/GalTechDev/GPUsync/blob/main/gpusync/compiler/base.py) — La base commune (`BaseTranspiler`)
- Dérive de `ast.NodeVisitor` (analyseur d'Arbre Syntaxique Abstrait standard de Python).
- Contient toute la logique de visite syntaxique commune (boucles `for/while`, expressions mathématiques binaires, assignations, structures conditionnelles `if/else`, typages, commentaires/docstrings et écritures).
- **Indépendance des backends** : Ne contient aucun embranchement `if self.backend == "opencl"` ou similaire. Toute la logique spécifique est déléguée aux sous-classes via le crochet `resolve_special_call`.

### B. [compiler/opencl.py](https://github.com/GalTechDev/GPUsync/blob/main/gpusync/compiler/opencl.py) — Le traducteur OpenCL (`OpenCLTranspiler`)
- Spécifie les fonctions intrinsèques OpenCL (comme `fmin`, `fmax`, `fabs`).
- Injecte du code d'émulation pour les opérations atomiques flottantes en mémoire globale et locale (`atomic_add_float`), qui ne sont pas natives en OpenCL 1.2.
- Gère la compilation finale en chaîne C99 prête à être compilée par PyOpenCL.

### C. [compiler/cuda.py](https://github.com/GalTechDev/GPUsync/blob/main/gpusync/compiler/cuda.py) — Le traducteur CUDA (`CUDATranspiler`)
- Spécifie les fonctions intrinsèques CUDA (comme `fminf`, `fmaxf`, `fabsf`).
- Gère les spécificateurs CUDA (`extern "C" __global__ void`, `__shared__`).
- Gère l'activation bas niveau des Tensor Cores (`wmma::fragment`, `mma_sync`) ainsi que la copie asynchrone matérielle `cp_async`.

### D. [compiler/llvm.py](https://github.com/GalTechDev/GPUsync/blob/main/gpusync/compiler/llvm.py) — Le traducteur CPU LLVM JIT (`LLVMTranspiler`)
- Génère les signatures de fonctions et instructions C/LLVM pour le processeur hôte (CPU).
- Permet l'exécution optimisée JIT multi-cœurs sans aucun GPU ni driver graphique requis.

### E. [compiler/llvm_cuda.py](https://github.com/GalTechDev/GPUsync/blob/main/gpusync/compiler/llvm_cuda.py) — Le traducteur LLVM NVPTX GPU (`LLVMCUDATranspiler`)
- Utilise la cible `nvptx64-nvidia-cuda` de `llvmlite` pour transpiler l'AST en code assembleur binaire/texte **NVIDIA PTX**.
- Contourne le compilateur C++ NVRTC pour injecter du binaire PTX directement dans le driver NVIDIA CUDA (`cuModuleLoadData`).

### F. [compiler/main.py](https://github.com/GalTechDev/GPUsync/blob/main/gpusync/compiler/main.py) — Point d'entrée et Décorateurs
- Expose `@gpusync_kernel` et `@gpusync_kernel_from_source`.
- Implémente la méthode **`kernel.map_out_of_core(dataset, scheduler)`** (support de tableaux NumPy et de générateurs `yield` pour streaming disque NVMe).
- Assemble l'arbre syntaxique, délègue la génération aux modules, instancie la tâche (`AsyncTask`) et l'encapsule dans le décorateur de thread `@auto_sync`.

## Le mécanisme de délégation : `resolve_special_call`

Pour éviter de dupliquer la logique ou de polluer la classe de base, nous utilisons un patron de conception par délégation (Hook) :

```python
# Dans BaseTranspiler.visit_Call
special_translation = self.resolve_special_call(func_name, node, args)
if special_translation is not None:
    return special_translation
```

Chaque compilateur spécifique implémente `resolve_special_call` et renvoie la traduction exacte dans son langage cible ou `None` pour se replier sur la traduction générique commune.
