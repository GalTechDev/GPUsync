# 1. Architecture du Compilateur AST

Le compilateur de GPUsync est un compilateur Juste-à-Temps (JIT) qui convertit le code Python en kernels natifs CUDA C++ et OpenCL C99 à la volée. Cette approche permet au développeur de coder dans une syntaxe Python épurée tout en profitant des performances brutes des GPUs.

---

## Structure du sous-package `gpusync/compiler/`

Le compilateur est structuré en plusieurs modules sous [gpusync/compiler/](https://github.com/GalTechDev/GPUsync/tree/main/gpusync/compiler) :

### A. [compiler/base.py](https://github.com/GalTechDev/GPUsync/blob/main/gpusync/compiler/base.py) — La base commune (`BaseTranspiler`)
- Dérive de `ast.NodeVisitor` (analyseur d'Arbre Syntaxique Abstrait standard de Python).
- Contient toute la logique de visite syntaxique commune (boucles `for/while`, expressions mathématiques binaires, assignations, structures conditionnelles `if/else`, typages et écritures).
- **Indépendance des backends** : Ne contient aucun embranchement `if self.backend == "opencl"` ou similaire. Toute la logique spécifique est déléguée aux sous-classes via le crochet `resolve_special_call`.

### B. [compiler/opencl.py](https://github.com/GalTechDev/GPUsync/blob/main/gpusync/compiler/opencl.py) — Le traducteur OpenCL (`OpenCLTranspiler`)
- Spécifie les fonctions intrinsèques OpenCL (comme `fmin`, `fmax`, `fabs`).
- Injecte du code d'émulation pour les opérations atomiques flottantes en mémoire globale et locale (`atomic_add_float`, `atomic_min_float_global`), qui ne sont pas natives en OpenCL 1.2.
- Gère la compilation finale en chaîne C99 prête à être compilée par PyOpenCL.

### C. [compiler/cuda.py](https://github.com/GalTechDev/GPUsync/blob/main/gpusync/compiler/cuda.py) — Le traducteur CUDA (`CUDATranspiler`)
- Spécifie les fonctions intrinsèques CUDA (comme `fminf`, `fmaxf`, `fabsf`).
- Gère les spécificateurs CUDA (`extern "C" __global__ void`, `__shared__`).
- Gère l'activation bas niveau des Tensor Cores (fragments `wmma::fragment`, chargements, produit matriciel `mma_sync`, stockages) ainsi que la copie asynchrone matérielle `cp_async`.

### D. [compiler/main.py](https://github.com/GalTechDev/GPUsync/blob/main/gpusync/compiler/main.py) — Point d'entrée et Décorateurs
- Expose `@gpusync_kernel` et `@gpusync_kernel_from_source`.
- Analyse les retours de la fonction pour déterminer automatiquement le nombre de buffers de sortie VRAM à allouer.
- Implémente le helper partagé `_compile_and_wrap_kernel` qui assemble l'arbre syntaxique, délègue la génération aux modules, instancie la tâche (`AsyncTask`) et l'encapsule dans le décorateur de thread `@auto_sync`.

## Le mécanisme de délégation : `resolve_special_call`

Pour éviter de dupliquer la logique ou de polluer la classe de base, nous utilisons un patron de conception par délégation (Hook) :

```python
# Dans BaseTranspiler.visit_Call
special_translation = self.resolve_special_call(func_name, node, args)
if special_translation is not None:
    return special_translation
```

Chaque compilateur spécifique implémente `resolve_special_call` et renvoie la traduction exacte dans son langage cible ou `None` pour se replier sur la traduction générique commune.
Exemple d'association mathématique :
- **OpenCL** : `min` -> `fmin(a, b)`
- **CUDA** : `min` -> `fminf(a, b)`

## Routage Dynamique des Dimensions (CUDA)

CUDA utilise une structure intégrée pour indexer les threads (`threadIdx`, `blockIdx`, `blockDim`). GPUsync abstrait cela via les fonctions OpenCL standard `get_global_id(dim)`, `get_local_id(dim)` et `get_group_id(dim)`.

Dans [compiler/cuda.py](https://github.com/GalTechDev/GPUsync/blob/main/gpusync/compiler/cuda.py), l'argument `dim` est résolu dynamiquement au moment de la transpilation (qu'il s'agisse d'un entier constant ou d'une variable résolue comme constante) pour générer l'axe adéquat :
- `dim = 0` -> Axe `x`
- `dim = 1` -> Axe `y`
- `dim = 2` -> Axe `z`

Par exemple, `get_global_id(1)` est automatiquement traduit en CUDA par : `(blockIdx.y * blockDim.y + threadIdx.y)`.

---

## Support des Tensor Cores (WMMA) et cp_async

Dans CUDA, le compilateur JIT de GPUsync sait intercepter des blocs spécialisés :
1. **Déclaration de Fragments** : `frag = wmma.fragment(...)` est transpilé vers la structure C++ `nvcuda::wmma::fragment`.
2. **Appels WMMA** : Les appels à `wmma.load_matrix_sync`, `wmma.mma_sync`, `wmma.store_matrix_sync` sont redirigés vers l'API matérielle correspondante.
3. **cp_async** : Les appels à `cp_async.copy_16` tirent parti du matériel de transfert asynchrone des architectures Ampère et supérieures (chargement global vers shared bypassant les registres).

---

## Retour des Kernels
Lorsqu'un kernel Python contient une instruction de retour comme `return a + b` ou `return a, b` (multi-retour) :
- Le transpilateur remplace automatiquement le `return` par l'assignation de variables de sortie réservées (`__out_0`, `__out_1`, etc.).
- L'adresse d'indexation dans ces buffers est résolue de manière globale selon l'identité de thread :
  - **OpenCL** : `__out_0[get_global_id(0)] = ...`
  - **CUDA** : `__out_0[blockIdx.x * blockDim.x + threadIdx.x] = ...`
